\begin{abstract}
Molt Petit is a consensus protocol for a fixed set of $n$ validators
that take turns producing blocks in time slots. A light client needs
very little: it keeps the genesis block and a clock, downloads a small
certificate from any source, checks that the certificate verifies and
that its newest block is recent, and then trusts every block at least
$n$ blocks deep. A chain is valid only if, in every past window of $n$
slots, at least two thirds of the validators produced a block. There
are no voting rounds, and finality is at a fixed depth.

All safety claims are machine-checked in Lean~4, under the assumptions
listed in Section~\ref{sec:assumptions} and a few implementation
assumptions named in Section~\ref{sec:impl}. The core claims cover the actual
Rust validator code, which is also the code proved inside the recursive
certificate (we trust the proof system to run it faithfully). Block ids
are checked by the hashing layer around the validator, an assumption we
name. The
key-rotation results are proved for the protocol model.

The attacker may obtain validators' signing keys at any time --- by
theft or by a temporary break-in --- and sign anything with them. Safety
holds as long as few enough keys are exposed around each window's own
time. Checking that the certificate is recent is essential: it is what
makes keys stolen long ago useless, and the proofs depend on it. No
valid chain can claim to be far ahead of real time.

Validators can rotate keys inside the protocol. Every rotation mode
recovers from lost keys. Against an attacker who steals keys and keeps
them forever, two modes stay safe given clearly stated duties for
operators, and clients still need only the genesis and a clock. With a
public rotation schedule, safety against theft follows directly from the
main theorem. With post-quantum signatures on ordinary hardware, the
verified consensus rule adds under $2\%$ to the cost of producing a
certificate.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Think of a light client that is offline most of the time: a wallet, an
embedded device, a bridge contract. Now and then it has to act on the
current state of a small consensus system. Today it has three options:
replay the history, trust a service, or verify a chain of committee
hand-offs.

Molt Petit is built so that this client needs only three things:
\begin{itemize}
\item the deployment's genesis block,
\item a clock, and
\item a small, constant-size \emph{certificate}, fetched from anyone.
\end{itemize}
If the certificate verifies and its newest block is recent, the client
can act on everything at least $n$ blocks below that newest block. Two
clients that follow this rule never act on conflicting blocks.

This guarantee is a machine-checked theorem about the validator code that
actually ships (\code{rust\_timed\_certified\_agreement}, and
\code{ts\_timed\_certified\_agreement} for the TypeScript version), under
the assumptions of Section~\ref{sec:assumptions}. One input is checked
outside that code: block ids are recomputed by the deployment's hashing
layer (Section~\ref{sec:impl}).

\paragraph{A small protocol.} A fixed roster of $n$ validators takes turns
producing blocks, one per time slot, in a public order. There are no
votes and no view changes. A chain is valid only if every past window of
$n$ slots contains blocks from at least two thirds of the validators. We
call this the \emph{density} rule (Section~\ref{sec:protocol}).

Density makes deep forks impossible while the fault budget holds, so a
block $n$ deep is final; finality is a fixed depth, not a probability.
Fork choice matters only for liveness: a node simply follows the highest
valid tip. A node never stores history. It holds a recursive proof that
the chain so far is valid, plus a short tail of signed blocks
(Section~\ref{sec:rules}).

\paragraph{Recent certificates matter.} Over a deployment's lifetime,
keys leak: machines are broken into and later cleaned, keys are stolen.
An attacker can use old leaked keys to sign a fake history; this is the
classic long-range attack. Molt Petit's fault budget counts, for each
window of $n$ slots, only the keys exposed during a short stretch of real
time around that window. A client that rejects certificates older than
$\varphi$ slots is exactly the client for whom later leaks do not matter.
And no attacker can prepare a valid chain that runs far ahead of real time to
get around this check (Section~\ref{sec:timed}).

\paragraph{Key rotation is part of consensus.} Every block says which
version of its producer's key signed it, so the chain orders key
rotations like any other event. Every rotation mode recovers from a lost
key, with no extra work for clients. Against an attacker who steals keys
and keeps them forever, two modes are safe: a public rotation schedule,
and a lockstep counter with key erasure. Each comes with a short, exact
list of operator duties, and their clients may sleep for as long as they
like. The third mode, reactive rotation, recovers from lost keys only; we
show why theft defeats it (Section~\ref{sec:rotation}).

\paragraph{Proofs about the shipped validator.} The validator is one Rust file. We
translate it into Lean~4 (with Charon and Aeneas) and prove the
translation sound against the model, so the core safety theorems are
about the code that runs. Block ids are checked outside it, by the
hashing layer; that is a named assumption. The key-rotation results are proved for the model today
(Section~\ref{sec:impl}). The same Rust source is the circuit of the
recursive proof, so the prover proves exactly the rule that was verified;
we trust the proof system to run that code faithfully. A separate
TypeScript implementation is proved sound against the same model, which
keeps the model independent of any one implementation. The build checks
that no theorem assumes anything beyond classical logic.

Measured with post-quantum signatures on ordinary hardware, the verified
consensus rule costs under $2\%$ of a certificate's proving time
(Section~\ref{sec:impl}). Formal consensus is effectively free on top of
the application.

\paragraph{The price.} The simplicity has costs, stated here and in
Section~\ref{sec:limitations}: the roster is closed and equally weighted;
a window without enough blocks halts the chain, by design; and safety
relies on correct clocks rather than holding under arbitrary network
delays. Where these trades are acceptable (permissioned systems, bridges,
fleets of devices), the result is a consensus layer whose client rule
fits in one sentence, and whose proofs re-check from a fresh checkout.
The next section states what operators and clients must do, mode by
mode, before any definitions.

\section{How to run it}
\label{sec:opmodel}

This section says what operators and clients must do. The rest of the
paper makes it precise.

One protocol runs throughout. A fixed roster of $n$ validators produces
blocks in public round-robin slots. Every block states which version of
its producer's key signed it. A node holds a constant-size certificate
plus a short tail of recent signed blocks. A verifier accepts a chain
only if it is valid and its newest block is recent, at most $b$ slots
old on the verifier's own clock. It then trusts everything $n$ blocks
deep.

Key rotation is built in. A deployment picks one of three rotation
\emph{modes}. The modes differ in one rule, the \emph{pin}: the lowest
key version a block may use (modes 1 and 2), or the exact version for
each window of slots (mode 3). The pin decides when a retired key stops
being usable.

The three modes behave the same unless keys are \emph{stolen}.
Validators rotate keys; clients never react to rotations. Every client
duty below is a fixed rule in time, not a response to an event.

\paragraph{Lost keys: every mode is safe.}
Any attacker in this paper can make a validator \emph{lose} its key:
destroy it, jam its signer, or force a rotation. Against that, all three
modes give the same client contract: \textbf{keep the genesis and a
clock, and sleep as long as you like}. Losing a key changes none of the
assumptions of Theorem~\ref{thm:lc}, so each mode's validator inherits it
(Theorem~\ref{thm:keyloss}). The validator that lost its key recovers
through its mode: a new key version in mode 1, the next scheduled
generation in mode 2, the next lockstep switch in mode 3. In mode 1, Lean
proves that once it has a new registered key, its next slot extends its
valid chain with a valid block, provided at most $\fmax$ slots per window
failed and the other honest validators kept every window dense while it
was out (\code{liveness\_produce\_blockK},
Assumption~\ref{ass:delivery}).

\paragraph{Mode 1: reactive rotation.}
Validators rotate whenever they choose, routinely or after losing a key.
Nobody knows in advance when a rotation will happen. Clients keep the
genesis and a clock and get the lost-key guarantee above, and nothing
more.

Mode 1 is \textbf{not safe against theft}. An attacker who steals the
retired keys of enough validators can forge a recent fork that branches
off before those rotations (Section~\ref{sec:rotation}). A deployment
that must survive theft runs mode 2 or mode 3.

\paragraph{Mode 2: scheduled rotation.}
The key version in force at each slot is a \emph{public function of the
slot}, published before the deployment starts. Everyone knows the whole
schedule in advance, and the validator rejects versions below it.

In every mode, signing keys are derived from one offline master key per
validator (Section~\ref{sec:protocol}). Mode 2 adds timing: the operator
derives each period's key (a \emph{generation}) just before that period
(its \emph{era}) begins. The theft theorem accounts for this through its
fault budget instead of assuming it (Section~\ref{sec:rotation}).

The client keeps the genesis, a clock, and the schedule. It may stay
offline as long as it likes and sync whenever it wakes up. There is no
trusted checkpoint, no required check-in rhythm, and no key erasure.

\paragraph{Mode 3: lockstep rotation.}
There is no schedule at all. The roster moves one shared generation
counter forward whenever it chooses. The slots are cut into fixed
windows of $n$ slots. A valid chain never mixes generations inside one
window, and the counter never goes back. At each switch, retired keys
are physically destroyed, in hardware security modules or RAM-only
storage; storage that does not truly erase does not qualify.

The client keeps the genesis and a clock, even less than in mode 2, and
may sleep as long as it likes. The price is paid by operators: they must
coordinate the switches, and erasure must be real. In return, erasure
earns a finer fault budget, counted per generation
(Section~\ref{sec:rotation}).

\section{The protocol}
\label{sec:protocol}

Lean names appear in \code{typewriter}. A cited theorem \code{xxx} is
proved as \code{MoltPaper.xxx} in the file \code{Paper/Proofs.lean}. Its
exact statement is \code{thm\_xxx}, in the file
\code{Spec/Statements.lean}. All results assume a non-empty roster,
$n \ge 1$. Every cited
definition is in \code{Spec/}: a few files that hold the definitions and
statements only, and that the rest of the development imports. The
precise forms live there; this paper explains them.

\subsection{Setting}

Time is divided into slots of fixed length $\tau$. A fixed, closed set of
$n$ validators, the \emph{roster}, produces blocks. Slot $s$ belongs to
validator $s \bmod n$ (\code{producer}). Who produces, and when, is
public and fixed; there is no leader election.

Two numbers derived from $n$ appear everywhere:
\begin{itemize}
\item the \emph{quorum} $\quorum = \lceil 2n/3 \rceil$, and
\item the \emph{fault budget} $\fmax = \lfloor (n-1)/3 \rfloor$: how many
  slots in any window of $n$ slots the attacker may control
  (Assumption~\ref{ass:budget}).
\end{itemize}

\subsection{Blocks and chains}

A block has six fields:
\[
B = (\mathit{slot},\ \mathit{height},\ \mathit{prev},\ \mathit{id},\
\mathit{contentsHash},\ \mathit{keyIndex}).
\]
\begin{itemize}
\item \code{contentsHash} commits to the payload (the transactions),
  which travels separately. No consensus rule looks inside it.
\item \code{keyIndex} is the version of the key that signed the block.
  Key rotation is therefore part of the chain itself.
\item \code{prev} is the parent's id, and \code{id} is the block's own
  hash.
\end{itemize}
The producer's signature travels next to the block, not inside it.

The deployment's hashing layer computes and checks ids by a fixed rule:
\[
\mathit{id} \;=\; H(\mathit{slot},\ \mathit{height},\ \mathit{prev},\
\mathit{parentSig},\ \mathit{contentsHash},\ \mathit{keyIndex}).
\]
The consensus rules treat ids as opaque, but two inputs of the hash
matter later:
\begin{itemize}
\item The \emph{parent's signature} is hashed in. So anyone building a
  fake chain must produce its signatures one after another, never all at
  once. Section~\ref{sec:timed} turns this into a bound in real time.
\item The \emph{key version} is hashed in. Otherwise two blocks that
  differ only in key version would have the same id as soon as anyone
  rotated a key.
\end{itemize}

A \emph{chain} is a sequence of blocks starting at a genesis block
(height zero, no parent). Heights go up by one, slots strictly increase,
and each block points to its parent's id (\code{linksOk},
\code{genesisOk}).

\subsection{The density rule}

There are no votes, and chains are not compared by length. Instead, a
chain must be \emph{dense}: every completed window of $n$ consecutive
slots must contain at least $\quorum$ of its blocks (\code{denseSoFar};
\code{validChain} combines this with the structure checks). A window is
complete once the chain's newest block has reached its end.

In plain terms: a chain counts as evidence only if, all along its
history, at least two thirds of the roster was building it.

Density is the whole safety mechanism. Suppose two chains split and both
stay dense. In any window after the split, each chain needs $\quorum$
blocks. Since $2\quorum > n + \fmax$, some slot in that window has a
block on \emph{both} chains and belongs to an honest validator. But an
honest validator signs only one block per slot. Every safety theorem in
Section~\ref{sec:results} is built on this counting argument, with
signatures, certificates and key rotation layered on top.

One more rule uses \code{keyIndex}: along a chain, a validator's key
version never goes down (\code{keyMonoOk}). Rotation only moves forward,
and the chain's order is the agreed order of rotations. Structure,
density and this rule together are \code{validChainK}, the chain
validity of this paper. A deployment completes the protocol by choosing
a rotation mode (Section~\ref{sec:rotation}).

\subsection{What a node holds}

A node does not keep history. It keeps a \emph{certified chain}: a
constant-size certificate plus a short tail of recent signed blocks. The
certificate vouches for everything below the tail. It exposes a
\emph{claim}: the slot, height and id of the newest block it covers,
plus a few blocks near that point so that density can be counted across
the join.

In our implementation the certificate is a \emph{recursive}
zero-knowledge proof. Each new proof checks the previous proof plus the
new blocks, so one small object covers an arbitrarily long history.

The rules use cryptography through two small interfaces that the
deployment provides:
\begin{itemize}
\item \code{SigOps}: sign and verify, plus the key map
  $\mathit{keyFor}(i,j)$, the public key of validator $i$ at version $j$
  (in the model, the map is a separate parameter, \code{KeyRegistry});
\item \code{CertOps}: verify a certificate, read its claim, and extend it
  by one checked block.
\end{itemize}

There is no key directory to trust: a verifier looks nothing up. Each
validator has one offline master key (a \emph{cold root}), created at the
deployment ceremony. A block's signature is really a bundle:
\begin{itemize}
\item the signing public key,
\item a delegation certificate, signed by the cold root, that binds this
  key to validator $i$ \emph{and version $j$}, and
\item the signature itself.
\end{itemize}
The delegation must name the version. A key that could answer for
several versions is exactly the key reuse that Section~\ref{sec:results}
must rule out.

\paragraph{What ``the signature verifies'' means.} The theorems read
signature checks the standard idealized way, as the ideal signature
functionality $\mathcal{F}_{\mathrm{SIG}}$~\cite{canettisig}: at a given
moment, a signature verifies only if someone has already produced it,
either the honest key holder or whoever holds a leaked key. A signature
scheme behaves this way exactly when it is EUF-CMA, the standard notion
of unforgeability~\cite{canettisig}. Assumption~\ref{ass:sig} states this
as an assumption (\code{hbridge}).

\subsection{The verifier rule}
\label{sec:verifier-rule}

Everything a light client does is one rule. Accept a certified chain if
and only if:
\begin{enumerate}
\item it is \emph{valid}: it passes the five checks of
  Section~\ref{sec:rules}, namely certificate, signatures, links,
  density, and key versions under the deployment's mode
  (\code{validCertifiedChain} plus the mode's key checks); and
\item it is \emph{recent}: its newest block is at most $b$ slots old on
  the verifier's clock.
\end{enumerate}
Then trust everything $n$ blocks below the newest block.

Every certificate-level theorem in this paper is about certified chains that
pass this rule. In Lean that appears as explicit hypotheses on each tail:
it links to the certificate's newest block (\code{hLink}) and block to
block (\code{hLinks}), its windows are dense (\code{hDense}), its blocks
are signed (\code{hSigned}), it meets the mode's key-version checks, and
its newest block is recent (\code{hRecent}).

If the verifier's clock is off by at most $\delta$ slots, the newest block
is at most $\varphi = b + \delta$ slots old in real time. This clock
comparison is the one line a deployment implements outside the verified
validator (Section~\ref{sec:limitations}).

Both halves are needed. Validity without recency lets in forks signed
with keys that leaked long afterwards: the long-range attack. Recency
without validity means nothing.

Choosing $b$ is a trade against the fault budget: a leaked key counts
against a window until $\varphi$ slots after it
(Assumption~\ref{ass:budget}). For example, $b = n$ with the prototype's
settings ($n = 7$, $\tau \approx 4$\,s) accepts tips up to about half a
minute old.

\section{The rules a node runs}
\label{sec:rules}

A node does three things with its certified chain: validate, produce and
select. All three are pure functions, with no I/O and no hidden state.
That is what lets one source serve as the reference implementation, the
Lean model and the circuit of the proof (Section~\ref{sec:impl}).

\paragraph{Validate} (\code{validCertifiedChain}). Accept a certified
chain only if:
\begin{enumerate}
\item the certificate verifies (\code{CertOps.verify}), one cheap check;
\item every block in the tail has a signature that verifies under the key
  of its slot's validator, at the key version the block states;
\item the tail links up: its first block extends the certificate's
  newest block (height one up, slot later, \code{prev} equal to that
  block's id), and so does each following block;
\item every window that completes inside the tail is dense, counting the
  certificate's boundary blocks plus the tail (\code{validSuffix});
\item key versions follow the rules: a validator's version never goes
  down (\code{keyMonoOk}), and every block meets the deployment's
  rotation pin. This is the only check that depends on the mode.
\end{enumerate}
The key-version checks are stated for full chains
(\code{validSignedChainK$'$} and its mode 2 and 3 variants). For modes 2
and 3 they are also proved at the certificate level
(\code{sched\_exposure\_certified\_agreement},
\code{lockstepGen\_recent\_certified\_suffix\_agreement}).

The model re-checks density from the genesis (\code{validChain}). A
running node checks only the windows that complete with each new block.
The two are equivalent, since earlier windows were checked when the
parent was accepted.

\paragraph{Produce} (\code{produceBlock?}). Only in its own slot, a
validator builds the next block on its current tip, signs it and appends
it. It ships the result only if it passes the same \code{validSuffix}
check every other node runs. So nothing on the production path has to be
trusted for safety: anything malformed it could emit is rejected
everywhere.

\paragraph{Select} (\code{selectChain}). Switch to a candidate chain only
if it is valid and its newest block is strictly higher. Selection never
affects safety: the theorems of Section~\ref{sec:results} hold for
\emph{any} two chains a verifier accepts, however they were chosen.
Selection matters only for liveness.

\paragraph{Compaction.} From time to time, a node folds the oldest tail
blocks into the certificate, keeping the tail short. Certificates are
proofs, not authority, so anyone may run the prover; one untrusted
proving service is enough. If proving falls behind, tails simply grow
until it catches up.

Certificates arrive in batches, so compaction looks for the newest cut
point for which it holds a verified certificate whose claim matches. The
compacted chain must pass \code{validCertifiedChain} like any other.
Like production, compaction needs no trust.

\section{What a deployment must provide}
\label{sec:assumptions}

Each assumption below appears as a hypothesis of the theorems that use
it; Lean's axiom check confirms that nothing else is assumed. The clock
is the one exception. Theorem~\ref{thm:lc} is stated at the real time $R$
at which the verifier checks; the rotation theorems use the verifier's
clock reading $\mathit{now}$; Assumption~\ref{ass:clock} links the two.
Mode 2 keeps these assumptions as they are, reading key exposure at the
scheduled key versions. Mode 3 uses adjusted forms, defined in
Section~\ref{sec:rotation}.

\paragraph{The attacker.}
\begin{itemize}
\item The attacker controls message delivery completely. Timely delivery
  matters only for liveness (Assumption~\ref{ass:delivery}).
\item The attacker obtains signing keys, by stealing them or by
  controlling a signer for a while, at any time it likes, within the
  budget of Assumption~\ref{ass:budget}.
\item A leaked key signs anything, for any slot, at any time.
\item The attacker's timing is unconstrained. Only the verifier's clock
  must be roughly right (Assumption~\ref{ass:clock}).
\end{itemize}
The attacker cannot sign with keys that have not leaked, find hash
collisions between real blocks, or forge certificates
(Assumptions~\ref{ass:sig}--\ref{ass:cert}).

\begin{assumption}[Exposure budget]\label{ass:budget}
A key is \emph{exposed} at a given moment if someone other than its
honest holder can sign with it then: the validator is malicious, the key
was stolen, or the attacker controls the signer. Exposure can start and
stop: a stolen key stays exposed, while control of a signer may come and
go.

The budget: in any $n$ consecutive slots, at most $\fmax$ slots have a
key that is exposed at some moment in a stretch of real time around that
window. The stretch starts $\ell$ slots before the window and ends
$\varphi$ slots after it. Exposure outside that stretch does not count
against the window.

For the usual roster size $n = 3\fmax + 1 \ge 4$, a lookback of
$\ell = n - 1 + \sigma$ is enough, where $\sigma$ is the honest clock lead
of Assumption~\ref{ass:sig}. The general condition is in the Lean.
\quad\textit{(Lean: \code{ExposureBounded}.)}
\end{assumption}

\begin{assumption}[Signatures]\label{ass:sig}
This assumption is about \emph{admissible} blocks: blocks the verifier's
own check would accept. A block is admissible when its signature verifies
and its id is correctly formed from its contents and its parent's
signature (Section~\ref{sec:protocol}).
\begin{enumerate}
\item[(a)] \emph{Custody.} While a key is not exposed, only its honest
  holder signs with it.
\item[(b)] \emph{Unforgeability.} A signature the verifier accepts at real
  time $R$ was produced by time $R$, by the honest holder or by whoever
  holds the leaked key. No one can make the verifier accept a signature
  that was never produced (\code{hbridge}).
\item[(c)] \emph{Honest signing.} An honest validator signs at most one
  block per slot, ever, and its clock runs at most $\sigma$ slots ahead of
  real time.
\end{enumerate}
\quad\textit{(Lean: \code{SigningExecutionOn}, \code{HonestClockOn},
\code{hbridge}.)}
\end{assumption}

Part (b) is the ideal-signature reading of Section~\ref{sec:protocol}; a
signature scheme provides it exactly when it is EUF-CMA. For part (c), an
honest validator keeps a persistent record of what it has signed, the
standard guard against signing twice after a restart. A slow clock costs
only liveness; a fast one is bounded by $\sigma$.

One more fact follows from how ids are formed: a block can be signed only
after its parent exists, because its id includes the parent's signature
(\code{chain\_order}).

Nothing limits a leaked key. It signs blocks for past or future slots, at
any time, as many as it likes; the only limit is how many keys are
exposed, and when (Assumption~\ref{ass:budget}). Junk that no verifier
accepts, such as a block with a malformed id or a copied id, is outside
the assumption, so it cannot break it. That is why the assumption speaks
only of admissible blocks.

With key rotation, a leaked \emph{retired} key still counts as exposure
of its validator. Section~\ref{sec:rotation} shows how the rotation modes
stop old keys from counting forever.

\begin{assumption}[Hash collision resistance]\label{ass:hash}
No two different admissible blocks that actually occur (or the genesis)
have the same id (\code{SigningExecutionOn.id\_inj}).
\quad\textit{(Lean: \code{SigningExecutionOn.id\_inj},
\code{SignedHashInjective}.)}
\end{assumption}

This is ordinary collision resistance in a form a proof can use.
Collisions do exist mathematically, since ids are shorter than blocks;
collision resistance says no one ever \emph{finds} one. Limiting the
statement to blocks that actually occur turns the second fact into the
first. Mode 3 and the untimed mode 2 theorem use the same assumption over
blocks that verify under the key version they state
(\code{SignedDeclared}).

\begin{assumption}[Certificate soundness]\label{ass:cert}
A certificate that verifies vouches for a claim built from the genesis
by adding one block at a time. Each step checks the links, the density
of newly completed windows, and the new block's signature and id.
\quad\textit{(Lean: \code{GroundedCert}.)}
\end{assumption}

This assumption does not assume a valid chain behind the certificate. A
proved lemma rebuilds that chain from the steps.

\begin{assumption}[Clock]\label{ass:clock}
The verifier's clock reads $\mathit{now}$, and real time is at most
$\delta$ slots ahead of it. Here $\delta$ covers clock error and network
delay together.
\end{assumption}

The verifier accepts a newest block when $\mathit{now} \le
\mathit{tip.slot} + b$. Theorem~\ref{thm:lc} then applies with
$\varphi = b + \delta$. A larger $b$ tolerates slower delivery, at the
price of a longer stretch of time in which exposure counts against each
window.

\begin{assumption}[Honest delivery, for liveness only]\label{ass:delivery}
The honest validators of each newly completing window were online, and
their blocks reached the next producer in time to be built on.
\quad\textit{(Lean: \code{HonestBlocksCover}.)}
\end{assumption}

\section{What the theorems guarantee}
\label{sec:results}

This section states the results in plain words. The exact statements are
in the Lean; each name in brackets points to one.

The order is:
\begin{enumerate}
\item light-client safety (Theorem~\ref{thm:lc});
\item no valid chain runs ahead of real time (Theorem~\ref{thm:forge}),
  the fact that the proof of Theorem~\ref{thm:lc} rests on;
\item what each rotation mode guarantees (Section~\ref{sec:rotation});
\item liveness (Section~\ref{sec:liveness}).
\end{enumerate}

\paragraph{Two kinds of attacker.} The \emph{exposure} attacker of
Section~\ref{sec:assumptions} obtains keys at any real time, by theft or
by temporary control, within the budget. Theorems~\ref{thm:lc}
and~\ref{thm:forge} face it, counting a slot as exposed if any of its
validator's keys is. Mode 2's theft theorem faces the same attacker, but
reads exposure at the scheduled key version: a stolen key exposes only
the slots it can still sign for. That is what rotation buys.

The \emph{key-stealing} attacker of Section~\ref{sec:rotation} is counted
differently, slot by slot: rented slots plus stolen key versions that are
still live. Mode 3 and the untimed mode 2 theorem face this attacker.

\paragraph{How far each result reaches.} Every result is a Lean theorem
about the model. Theorem~\ref{thm:lc}, with the same assumptions, is
also carried to both implementations by their soundness bridges (Section~\ref{sec:impl}):
\code{rust\_timed\_certified\_agreement} for the Rust validator, which
also covers its key-version checks, and
\code{ts\_timed\_certified\_agreement} for the TypeScript one. The other
results are, today, proved for the model only.

\paragraph{Where to check.} Each result the paper cites as \code{xxx} is
stated as \code{thm\_xxx} in \code{Spec/Statements.lean} and proved as
\code{xxx} in \code{Paper/Proofs.lean}. The statements and every
definition they use live in \code{Spec/}, which contains no proofs and is
imported by the rest of the development. The build checks the axioms of
every proof, so it fails if any proof ever assumes more than classical
logic.

\subsection{Light-client safety}
\label{sec:lc}

\begin{theorem}[Recent chains share their deep blocks; Lean
\code{timed\_light\_client\_safety}]\label{thm:lc}
Fix the roster size $n \ge 1$, a genesis $G$, a freshness $\varphi$, an
honest clock lead $\sigma$, and a lookback $\ell$ with $\ell \ge n - 1$
and $\ell \ge n + \fmax + \sigma + 1 - \quorum$. Assume:
\begin{itemize}
\item \emph{Signing} (\code{SigningExecutionOn}): Assumption~\ref{ass:sig}
  (a) and (c) and Assumption~\ref{ass:hash}, for admissible blocks.
  Signing happens at real times; while a key is unexposed, it signs at
  most one admissible block per slot (\code{honest\_once}); a block is
  signed only after its parent exists (\code{chain\_order}); and no two
  admissible blocks share an id (\code{id\_inj}).
\item \emph{Clocks} (\code{HonestClockOn}): honest clocks run at most
  $\sigma$ slots ahead.
\item \emph{Budget} (\code{ExposureBounded}~$n$~$\ell$~$\varphi$):
  Assumption~\ref{ass:budget}.
\item \emph{Unforgeability} (\code{hbridge}):
  Assumption~\ref{ass:sig}(b), with the verifier checking at real
  time $R$.
\item \emph{Two accepted chains}: each is a certificate
  (\code{GroundedCert}) plus a non-empty tail the verifier accepts, as
  in Section~\ref{sec:rules}.
\item \emph{Both are recent}: $R \le \mathit{tip.slot} + \varphi$ for
  both tips.
\end{itemize}
Then the two full chains (\code{GroundedHistory}) agree on every block at
least $n$ blocks below the lower tip.
\end{theorem}

The result also covers a chain the node \emph{produced} rather than
received, because production ships nothing that would fail the
validator (Section~\ref{sec:rules}).

\paragraph{Why it holds.} The proof is the classic quorum count, with the
timing made explicit.
\begin{enumerate}
\item Take the last full window of $n$ slots below the lower tip. Each
  chain has at least $\quorum$ blocks there, so at least $2\quorum - n
  \ge \fmax + 1$ slots have a block on both chains.
\item Suppose all those pairs differ. Then each of those slots had its
  key exposed at one of the two signing times, by
  \code{honest\_once}.
\item Each signature was made by time $R$, so at most $\varphi$ slots
  after the window. By Theorem~\ref{thm:forge}, each was made no earlier
  than $\ell$ slots before the window.
\item That is $\fmax + 1$ exposed slots within one budget stretch, which
  the budget forbids. So the chains share a block in the window.
\item Shared ids and collision resistance then make them agree on
  everything below that block.
\end{enumerate}

\paragraph{Why the lookback.} Without a lookback, every exposure up to
$\varphi$ slots after a window would count against it, however long ago
it happened. Under that simpler, cumulative budget
(\code{ExposureBoundedEver}) agreement holds without any assumption on
clocks, for full chains: two valid chains from the genesis, whose
non-genesis blocks are admissible and all exist by time $R$, with the other assumptions of Theorem~\ref{thm:lc}
(\code{exposure\_agreement\_ever\_on}). We have not proved its
certificate form. A bound on early signing also
holds there, but it still assumes honest clocks and depends on their
lead: for a non-genesis block $B$ of a chain as in Theorem~\ref{thm:forge},
with $B.\mathit{slot} \ge n - 1$,
$B.\mathit{slot} \le r + n + \fmax + \sigma + 1 - \quorum$
(\code{exposure\_no\_early\_signing\_ever\_on}). The
lookback lets a signer that was compromised and then cleaned up stop
counting against later windows. The honest clock bound is its price.

\subsection{No chain runs ahead of real time}
\label{sec:timed}

The recency check needs one more fact. An attacker must not be able to
build a chain early whose tip will look recent later.

This rests on the id rule (\code{chain\_order}). A block's id includes
its parent's signature, so a block can be signed only after its parent
exists. Predicting someone else's signature without their key would be a
forgery, even for a deterministic signature scheme.

\begin{theorem}[No valid chain runs ahead of real time; Lean
\code{no\_early\_signing}]\label{thm:forge}
Assume the signing, clock and budget assumptions of
Theorem~\ref{thm:lc}, including the lookback condition. Take a valid
chain from $G$ whose blocks are admissible and all exist by some real
time. If one of its blocks $B \ne G$ was signed at real slot $r$, then
\[
B.\mathit{slot} \;\le\; r + \ell .
\]
With the smallest allowed lookback, $\ell = n - 1$ (for
$n = 3\fmax + 1 \ge 4$ and $\sigma \le \fmax - 1$), no valid chain gets
more than $n - 1$ slots ahead of real time.
\end{theorem}

\paragraph{Why it holds.} By induction along the chain. Suppose $B$ was
signed more than $\ell$ slots before its slot.
\begin{itemize}
\item Its signer was not honest, since honest clocks lead by at most
  $\sigma \le \ell$. So $B$'s key was exposed at time $r$.
\item The window of $n$ slots ending at $B$ is complete, so it holds at
  least $\quorum$ blocks: $B$ and its ancestors, all signed by time $r$.
\item An honest block among them has slot at most $r + \sigma$. An
  exposed one was, by induction, not signed early either, so its
  exposure counts against the window's budget.
\item Either way, too few blocks remain to reach $\quorum$.
\end{itemize}
(For $n = 1$, the same count runs on the window of $B$'s predecessor.)

\paragraph{What this does not rule out.} A patient attacker can still
collect signatures into a long fork, by exposing keys long after the
slots it signs. Such a fork is stale. Late exposure does not count
against old windows, but it cannot produce recent blocks either, because
recent windows have their own budget. The recency check refuses exactly
such a stale fork. Theorem~\ref{thm:forge} rules out the reverse: a fork
prepared early to look recent later.

\subsection{Key rotation}
\label{sec:rotation}

Most of key rotation is already part of the protocol. Each block states
its key version (\code{keyIndex}, Section~\ref{sec:protocol}), and a
validator's version never goes down (\code{keyMonoOk}). A deployment adds
one more rule, the \emph{pin}: a lower bound on the version a block may
state. In mode 3 the bound is exact for each grid window. The pin is what
makes a retired key \emph{dead} rather than merely old.

The three modes differ in one thing only: \textbf{what sets the pin}.
\begin{itemize}
\item Mode 1: the chain itself.
\item Mode 2: the slot number, through a fixed schedule.
\item Mode 3: a roster-wide counter, read off the signatures.
\end{itemize}
That one choice decides what a light client must hold. For each mode we
give the rule, what it guarantees, what the operator must do, and what
the client must do.

\paragraph{Lost keys, in every mode.} A \emph{lost} key (destroyed, not
stolen) gives the attacker nothing. The validator rotates, and the
protocol already supports that. With nothing stolen, the corruption the
theorems count shrinks to rented slots alone, in every mode
(\code{badKeyrot\_lossOnly}, \code{badSched\_lossOnly}; mode 3 inherits
mode 2's count). Theorem~\ref{thm:lc} then applies to each mode's
validator unchanged: \code{keyrot\_loss\_agreement} (mode 1,
Theorem~\ref{thm:keyloss}), \code{sched\_loss\_agreement} (mode 2) and
\code{lockstep\_loss\_agreement} (mode 3), each for chains with
correctly formed ids (\code{hFormed}), as in Theorem~\ref{thm:keyloss}. A client holding only the
genesis and a clock gets the guarantees of
Sections~\ref{sec:lc}--\ref{sec:timed}, with no anchor and any pin.

\paragraph{Stolen keys.} Theft is harder. A stolen key of \emph{any}
version signs anything, for any slot, forever: we assume no forward
security~\cite{forwardsec}. Modes 2 and 3 are built for this attacker.
\begin{itemize}
\item Mode 2 needs nothing beyond the assumptions of
  Theorem~\ref{thm:lc}, read at the schedule.
\item Mode 3, and an older untimed form of mode 2, count theft
  differently: per window of $n$ slots, at most $\rho$ \emph{rented}
  slots plus at most $T$ validators with a \emph{live} key stolen, with
  $\rho + T \le \fmax$.
\end{itemize}
A rented slot is one the attacker controls for that slot only and then
loses. If a rented device is made to sign for other slots, that key
version counts as stolen, in $T$. A stolen key is \emph{live} if its
version is at least the one in force. So a stolen key stops counting as
soon as its retirement takes force: healing is built into the count
(\code{badSched}).

This count also needs \emph{version independence}: stealing version $j$
reveals nothing about any later version $j' > j$. Key-insulated
signatures~\cite{keyinsulated,keyinsulatedsig} provide it. Hash collision
resistance (Assumption~\ref{ass:hash}) is used over blocks that verify
under the version they state (\code{SignedDeclared}).

\begin{assumption}[Honest custody, per key]\label{ass:rotation-honest}
This is used by mode 3 and the untimed form of mode 2. Take a slot $s$
that is not rented, and a key version $j$ of its validator $i$ that was
never stolen. Then:
\begin{itemize}
\item every block for slot $s$ that verifies under version $j$ was
  signed by $i$'s own signing device;
\item that device signs at most one block per slot, ever, keeping a
  persistent record;
\item it states the version the mode's rule assigns to that slot.
\end{itemize}
\quad\textit{(Lean: \code{SchedUnforgeable}, \code{SchedCoreUnforgeable}.)}
\end{assumption}

The device's clock may run up to $\sigma$ slots ahead, as in
Assumption~\ref{ass:sig}. The assumption covers only the honest path:
once a key is rented or stolen, the attacker is free of it.

Why it is assumed rather than derived from Theorem~\ref{thm:lc}'s
assumptions: it is stated per key version, and one slot can have several
eligible key versions, only one of which verifies. So one key being safe
does not make the slot safe. Lean checks this gap
(\code{badSched\_single\_key\_safe\_not\_enough}).

\subsubsection*{Mode 1: rotate when you want}

\paragraph{The rule.} A validator rotates whenever it chooses, by
signing under a higher version. The pin comes from the chain being
checked. Validator $i$'s version \emph{in force} at a slot
(\code{inForce}) is the highest version $i$ has used in the chain's
\emph{confirmed} part, meaning blocks at least $n$ slots old. No block may
state less (\code{validSignedChainK$'$}).

Why $n$ slots: every chain must switch at the same moment, and ``the
announcing block is confirmed'' is that moment. At depth $n$, all
accepted chains provably agree. (The Lean proof allows any depth of at
least $n$.) At the prototype's settings, a rotation takes effect in under
half a minute.

\paragraph{What it guarantees: recovery from key loss.} A validator that
loses its key signs its next block under a higher registered version,
and production resumes (\code{liveness\_produce\_blockK}). The new
version must already be in the deployment's key registry, for instance
delegated from the validator's cold root. The verifier never learns a new
key from the chain. Loss changes none of the assumptions of
Theorem~\ref{thm:lc}, so mode 1 inherits it directly.

\begin{theorem}[Mode 1 under key loss; Lean
\code{keyrot\_loss\_agreement}]\label{thm:keyloss}
Assume the signing, clock, budget and unforgeability assumptions of
Theorem~\ref{thm:lc} (\code{SigningExecutionOn}, \code{HonestClockOn},
\code{ExposureBounded} with its lookback condition, \code{hbridge} at
real time $R$). Here a block is admissible when it verifies under the
version it states (\code{SignedDeclared}) and its id is correctly formed.
Take two chains from the genesis $G$ that pass the mode-1 validator
(\code{validSignedChainK$'$}, at any confirmation depth), with correctly
formed ids (\code{hFormed}), and whose tips are both recent:
$R \le \mathit{tip.slot} + \varphi$. Then they agree on every block at
least $n$ blocks below the lower tip.
\end{theorem}

\paragraph{What it does not guarantee: key theft.} Mode 1 is not safe
against key theft, and we claim nothing there. The pin keeps a retired
key dead only on chains that contain its retirement. A fork that
branches off before the retirements is not bound by it.

The attack is simple. Validators stop guarding retired keys. An attacker
who later steals the retired keys of a quorum builds a dense fork from a
point before those rotations, with recent-looking slots, and shows it to
a client holding only the genesis and a clock. The fork passes the
mode-1 validator and the recency check, yet differs from the real chain
arbitrarily deep. No budget on the real chain rules it out, since the
stolen keys were retired there.

A deployment that must survive key theft runs mode 2 or mode 3.

\subsubsection*{Mode 2: rotate on a schedule}

\paragraph{The rule.} The version in force at slot $s$, called the
\emph{generation}, is fixed in advance: $\mathit{gen}(s) = \lfloor s/E
\rfloor$ for an era length $E$. It depends on the slot alone, is the same
on every chain, and is built into the verifier, never taken from the
network. The validator adds one check:
$\mathit{gen}(\mathit{slot}) \le \mathit{keyIndex}$
(\code{validSignedChainSched}).

Since the pin reads nothing from any chain, a fork \emph{cannot} disagree
with the real chain about which keys are retired. The attack on mode 1
is impossible.

\paragraph{What it guarantees: safety under theft.} Mode 2 needs no
assumption beyond those of Theorem~\ref{thm:lc}. It only reads exposure
at the schedule. Slot $s$, with validator $i = s \bmod n$, is
\emph{exposed} at real time $r$ (\code{schedExposed}) when, at $r$:
\begin{itemize}
\item the attacker controls validator $i$ (written
  $\mathit{Controlled}(i, r)$), or
\item someone other than $i$ can sign with one of $i$'s keys of version
  $j \ge \mathit{gen}(s)$ (written $\mathit{Stolen}(i, j, r)$).
\end{itemize}
Both may change over time arbitrarily. A block is \emph{admissible} when
it verifies under the version it states, that version is at least
$\mathit{gen}$ of its slot (\code{SchedAdmissible}), and its id is
correctly formed. Assumption~\ref{ass:sig} is needed for admissible
blocks only (\code{SigningExecutionOn}, \code{HonestClockOn}). A block
signed with a key already retired for its slot is not admissible: no
validator accepts it.

\begin{theorem}[Mode 2 under key theft; Lean
\code{sched\_exposure\_agreement},\hfil\penalty0
\code{sched\_exposure\_certified\_agreement}]\label{thm:sched}
Fix a schedule $\mathit{gen}$ and any histories $\mathit{Controlled}$
and $\mathit{Stolen}$. Assume, with exposure and admissibility read as
above, the signing, clock, budget and unforgeability assumptions of
Theorem~\ref{thm:lc} (\code{SigningExecutionOn}, \code{HonestClockOn},
\code{ExposureBounded}~$n$~$\ell$~$\varphi$ with its lookback condition,
\code{hbridge} at real time $R$). Take two chains from the genesis $G$
that pass the mode-2 validator (\code{validSignedChainSched}), with
correctly formed ids (\code{hFormed}), and whose tips are both recent:
$R \le \mathit{tip.slot} + \varphi$. Then they agree on every block at
least $n$ blocks below the lower tip.

The same holds for two certificate-plus-tail presentations, as in
Theorem~\ref{thm:lc}, with certificates that also check the pin at each
step (\code{GroundedCertSched}, \code{GroundedHistorySched}) and
admissible tail blocks.
\end{theorem}

Both forms come from one generalisation of the core, proved once.
Theorems~\ref{thm:lc} and~\ref{thm:forge} hold, with all their other
assumptions, when Assumption~\ref{ass:sig} is required only of blocks
meeting some per-block test that every block of both chains passes
(for full chains, \code{exposure\_agreement\_on} and
\code{exposure\_no\_early\_signing\_on}; for certificates,
\code{exposure\_certified\_agreement\_on}).

That restriction matters. Required of \emph{every} signed block, the
assumption would fail as soon as a stolen key signed a block with a
made-up parent. And because mode 2 counts exposure per slot, over every
version that may sign for it, the gap between ``one key is safe'' and
``the slot is safe'' never arises.

\paragraph{What the budget charges.} The schedule makes the budget of
Assumption~\ref{ass:budget} precise.
\begin{itemize}
\item A stolen version $j$ exposes only slots whose generation is at
  most $j$.
\item It counts against every window whose stretch of real time reaches
  the theft, from about the time of the theft until era $j$ ends. It
  never counts against a window whose stretch ended before the theft.
\item A retired key exposes nothing, stolen or not. No erasure is
  needed.
\item A key made ahead of its era and stolen early counts until its era
  ends.
\item A stolen \emph{cold root} gives every later version of its
  validator, so that validator counts as exposed in every later window,
  like a malicious one.
\end{itemize}
So careful key provisioning is not an extra assumption; it is how an
operator stays within the budget.

One modelling rule remains: $\mathit{Stolen}$ must list every version the
attacker can sign with. Version independence keeps that list as short as
what was actually taken.

\paragraph{Operator duties.} Keep one offline cold root per validator.
Delegate each generation's signing key just in time for its era; then a
theft costs only the rest of that era. The era length $E$ is a dial:
longer eras mean fewer cold-root ceremonies, but a stolen live key counts
for longer. A retired key is harmless by rule, not by secrecy. Separately,
a chain whose tip states a generation whose era ended longer ago than
the recency window fails the recency check
(\code{sched\_oldkey\_fork\_stale}).

\paragraph{What breaks first.}
\begin{enumerate}
\item A schedule taken from the network. The pin must be built into the
  verifier; a zero schedule from a peer would readmit every retired key.
\item Theft of the \emph{current} generation, which counts until its era
  ends. Size the budget and $E$ together.
\item A stolen cold root, which costs its validator for good.
\end{enumerate}

\paragraph{Without a genesis.} An older, \emph{untimed} form lets a
full-chain client work without holding the genesis. It has no real-time
model of signing, though it still uses the recency check. Its results are
\code{sched\_recent\_tip\_ancestor\_agreement\_horizon},
\code{sched\_recent\_tip\_ancestor\_mem\_horizon} and
\code{sched\_recent\_genesis\_agreement\_horizon}. It shows:
\begin{itemize}
\item at equal tip heights, two accepted chains longer than $n$ blocks
  agree on the block $n$ below each tip;
\item at unequal heights, if the lower chain is longer than $n$ blocks,
  its block $n$ deep is also a block of the taller chain, at least $n$
  deep there;
\item two accepted chains longer than $n$ blocks share their genesis.
\end{itemize}
It uses Assumption~\ref{ass:rotation-honest} (\code{SchedUnforgeable}),
hash collision resistance (Assumption~\ref{ass:hash}), the recency check
on both tips ($\mathit{now} \le \mathit{tip.slot} + \Delta$), and the
$\rho + T$ count, from some starting slot $H$ on
(\code{ByzantineBoundedFrom}~$H$~$n$~(\code{badSched}~\dots), with
$H + n \le \mathit{tip.slot} + 1$ for both tips). Its count charges a stolen,
not-yet-retired key from the start of time, so early theft and cold-root
custody must be assumed rather than charged. Its certificate form is
\code{sched\_recent\_certified\_suffix\_agreement\_horizon}, which, like
every certificate, still starts from the genesis. Otherwise
Theorem~\ref{thm:sched} supersedes it.

\paragraph{A mode-2 deployment, end to end.}
\begin{itemize}
\item \emph{Setup.} Each validator makes its cold root offline. The
  deployment publishes $\mathit{gen}(s) = \lfloor s/E \rfloor$, with $E$
  one week of slots, say.
\item \emph{Every week.} Each cold root signs one delegation for the
  coming generation and goes back in the safe. A live key never exists
  much before its era.
\item \emph{Clients.} Wallets hold the genesis, a clock and
  $\mathit{gen}$. They may sleep for months and sync on waking.
\item \emph{What must hold.} Assumption~\ref{ass:sig} for admissible
  blocks, collision resistance (Assumption~\ref{ass:hash}), the clock
  (Assumption~\ref{ass:clock}), and the budget
  (Assumption~\ref{ass:budget}) over mode-2 exposure. A stolen live key
  counts for at most the rest of its week plus the window's stretch; size
  the budget for that.
\item \emph{What you get.} By Theorem~\ref{thm:sched} and the parent-id
  links (\code{same\_block\_same\_prefix}), any two accepted recent
  chains agree on everything at least $n$ blocks below the lower tip,
  whatever happened while the wallet slept. A certificate client gets the
  same (\code{sched\_exposure\_certified\_agreement}).
\end{itemize}

\subsubsection*{Mode 3: rotate together, at any time}

\paragraph{The rule.} There is no schedule. The roster moves one shared
generation counter forward whenever it decides to, for example after an
incident or by a governance decision. Validity enforces only the
discipline of the switch (\code{noMixing}, \code{validSignedChainLock}):
\begin{itemize}
\item within each grid window (slots $[Wn,\,Wn{+}n)$, a fixed grid, not
  a sliding window), all blocks state the same generation;
\item the generation never goes down from one grid window to the next.
\end{itemize}
The verifier never learns when switches happen. It reads each grid
window's generation off the signatures.

\begin{theorem}[Lockstep safety; Lean
\code{lockstep\_client\_safety}]\label{thm:lock}
Assume:
\begin{itemize}
\item the roster follows one counter that never goes down, honest
  signatures state their grid window's value, and the genesis states its
  starting value;
\item hash collision resistance;
\item the $\rho + T \le \fmax$ budget, read at the counter one grid
  window back, over Assumption~\ref{ass:rotation-honest} for the pin-free
  validator;
\item both tips recent: $\mathit{now} \le \mathit{tip.slot} + \Delta$;
\item chains longer than $n$ blocks (\code{hLong}): both chains at equal
  heights, the lower one at unequal heights.
\end{itemize}
Take two chains from the genesis that pass the lockstep validator. Then,
with no trusted recent checkpoint:
\begin{itemize}
\item at equal tip heights (\code{hTipHeight}), they agree on the block
  $n$ below each tip;
\item at unequal heights (\code{lockstep\_recent\_tip\_ancestor\_mem}),
  the lower chain's block $n$ deep is a block of the taller chain, at
  least $n$ deep there.
\end{itemize}
The client holds only the genesis and a clock; there is no schedule to
store.
\end{theorem}

\paragraph{Why it holds.} A Lean \emph{pinning} theorem
(\code{lockstep\_declares\_rosterGen}) shows that on any accepted recent
chain, every complete grid window states exactly the roster's counter.
A window at any other generation would need a quorum of attacker
blocks, which the budget does not allow. So every accepted mode-3 chain
also passes mode 2's validator, at the counter one grid window back, and
the untimed mode-2 results carry over.

\begin{theorem}[Lockstep safety, counted per generation; Lean
\code{lockstep\_client\_safety\_gen},\hfil\penalty0
\code{lockstepGen\_recent\_tip\_ancestor\_mem}]\label{thm:lock-gen}
Assume:
\begin{itemize}
\item the lockstep validator (\code{validSignedChainLock});
\item honest signatures state their grid window's counter;
\item hash collision resistance;
\item Assumption~\ref{ass:rotation-honest} for the pin-free validator;
\item at most $\rho$ rented slots per window and, for each generation $j$
  separately, at most $T$ validators whose generation-$j$ key is stolen,
  with $\rho + T \le \fmax$;
\item both tips recent: $\mathit{now} \le \mathit{tip.slot} + \Delta$;
\item chains longer than $2n$ blocks (\code{hLong}): both chains at equal
  heights, the lower one at unequal heights.
\end{itemize}
Then any two accepted chains agree:
\begin{itemize}
\item at equal tip heights (\code{hTipHeight}), on the block $2n$ below
  each tip (\code{lockstep\_client\_safety\_gen});
\item at unequal heights, the lower chain's block $2n$ deep is a block
  of the taller chain, at least $2n$ deep there
  (\code{lockstepGen\_recent\_tip\_ancestor\_mem}).
\end{itemize}
Through the parent-id links, two such chains longer than $2n$ blocks
agree on their whole common prefix, down to height $0$. No shared genesis
is assumed (\code{lockstepGen\_recent\_genesis\_agreement}).
\end{theorem}

\paragraph{Why it holds.} A second pinning theorem, needing neither
induction nor a genesis (\code{lockstep\_window\_declares\_rosterGen}),
shows that the last complete grid window below the lower tip states one
generation on both chains. The quorum count then runs on a window read at
a single generation (\code{window\_shared\_prefix}). The tip's own grid
window is not complete and cannot be used, which is why the depth is
$2n$: exactly $n + ((t{+}1) \bmod n)$ for lower tip slot $t$
(\code{lockstepGen\_shared\_prefix\_sharp}).

The two budgets are not comparable in general. The first gives the second
when the counter never skips a generation (\code{LockstepPackage.toGen}).

\paragraph{Operator duties.} Two, and they are this mode's real price.
\begin{itemize}
\item \emph{Moving together.} All honest signers follow the one counter.
  A split among them is an operational failure the theorems do not cover.
\item \emph{Real erasure} of retired keys at each switch.
\end{itemize}
Erasure earns its keep formally. With theft time-stamped, erasure says no
generation is stolen after the roster has moved past it
(\code{ErasureTimedLock}). That turns the count a deployment attests
while a generation is live into the per-generation count
Theorem~\ref{thm:lock-gen} needs (\code{genBound\_of\_preRetirementBound};
end to end, \code{lockstep\_client\_safety\_timed}). So a deployment
budgets $T$ validators lost \emph{per generation, while it is live}, not
$T$ over all time.

Mode 2 needs neither erasure nor provisioning discipline as a
hypothesis: its schedule makes retired keys harmless, and its budget
charges early theft directly. Mode 3 has no schedule, so it needs
erasure instead. Erasure that does not really happen is invisible to the
protocol. Keys kept in a hardware module, or only ever in RAM, are fine;
flash storage, which does not erase by overwriting, is not.

\paragraph{A mode-3 deployment, end to end.}
\begin{itemize}
\item \emph{Setup.} Each validator signs from a hardware module that
  destroys retired generations on a switch. The genesis states the
  counter's starting value.
\item \emph{Switches.} They are agreed out of band, after an incident or
  by governance. Every honest signer moves at the agreed grid-window
  boundary.
\item \emph{Clients.} They hold the genesis and a clock, nothing else,
  and may sleep for any length of time. On waking, they sync from a
  certificate plus a short tail, as in modes 1 and 2.
\item \emph{The certificate} carries the claim and the tip generation.
  For $n \ge 2$, the claim's own tail determines the generation
  (\code{groundedCertLock\_gen\_of\_tail},
  \code{groundedCertLock\_gen\_unique}). Only for $n = 1$ must the
  counter be attested with the claim; an unauthenticated counter would
  readmit a stolen retired key.
\item \emph{What must hold.} Assumption~\ref{ass:rotation-honest} for
  the pin-free validator, hash collision resistance, the clock
  (Assumption~\ref{ass:clock}), the moving-together discipline, and
  \emph{either} the $\rho + T$ budget read at the counter one grid window
  back (Theorem~\ref{thm:lock}, depth $n$), \emph{or}, at depth $2n$, at
  most $\rho$ rented slots per window and, for each generation $j$, at
  most $T$ validators whose generation-$j$ key is stolen while $j$ is
  live (Theorem~\ref{thm:lock-gen}; with time-stamped theft,
  \code{lockstep\_client\_safety\_timed}).
\item \emph{What you get.} Any two accepted chains agree on the lower
  chain's whole confirmed part, with no schedule and no anchor. At equal
  heights they agree on the block $n$ below each tip ($2n$ under the
  per-generation count); at unequal heights, the lower chain's confirmed
  block lies on the taller one; the parent-id links
  (\code{same\_block\_same\_prefix}) give the rest. In Lean:
  \code{lockstep\_client\_safety} and
  \code{lockstep\_recent\_tip\_ancestor\_mem}, through the pinning theorem
  \code{lockstep\_declares\_rosterGen}. For two certified chains that
  pass the verifier rule (Section~\ref{sec:verifier-rule}), tips recent included:
  \code{lockstep\_recent\_certified\_suffix\_agreement} at depth $n$ and
  \code{lockstepGen\_recent\_certified\_suffix\_agreement} at depth $2n$,
  with the certificate's counter pinned to the roster's once its grid
  window completes (\code{lockstep\_cert\_gen\_pinned}).
\end{itemize}

The modes and their main theorems are summarised in
Section~\ref{sec:opmodel}.

\paragraph{The limits of this subsection.}
\begin{enumerate}
\item Mode 1 has no guarantee under key theft (see above).
\item The mode-2 and mode-3 results are about the model. The Rust
  validator carries the mode-1 check (bridged in
  \texttt{Rust/BridgeK.lean}), but neither the schedule pin nor the
  lockstep rule.
\item Mode 3 and the untimed form of mode 2 rest on
  Assumption~\ref{ass:rotation-honest}, which is assumed, not derived:
  one safe key does not make a safe slot
  (\code{badSched\_single\_key\_safe\_not\_enough},
  \code{badKeyrot\_single\_key\_safe\_not\_enough}). Mode 2's theft
  theorem needs no such assumption; it uses Assumption~\ref{ass:sig}
  itself, for admissible blocks.
\end{enumerate}

\subsection{Liveness, and the slot time}
\label{sec:liveness}

Safety limits what a verifier can be made to accept. Liveness is about
progress. Its proofs use only the basic chain rules
(Section~\ref{sec:protocol}); no rotation assumption is involved.

\begin{theorem}[Liveness; Lean \code{production\_liveness},
\code{global\_liveness}]\label{thm:live}
Assume at most $\fmax$ slots in any $n$ consecutive slots belong to
failing validators (\code{ByzantineBounded}), and honest delivery
(Assumption~\ref{ass:delivery}).
\begin{itemize}
\item \emph{Locally:} when an honest validator holding an accepted chain
  reaches its slot, it produces a block, and the extended chain passes
  the same validator everyone runs.
\item \emph{Globally:} in a synchronous honest run within the budget,
  from a well-formed genesis,
  where each honest block reaches the next honest validator within its
  slot, the chain is accepted with one block per honest slot. So it
  reaches any height, and every block eventually becomes $n$ deep.
\end{itemize}
\end{theorem}

The fork-choice rule, adopting the valid chain with the highest tip, is
what makes honest blocks merge into the single chain the global form
assumes. A full model of a network with many chains is future work.

\paragraph{The slot time.} One number remains: the slot length $\tau$.
Prover cost sets it, not network latency. The proving cost has a fixed
part per certificate and a part per block, both non-negative. A slot must be long enough for
the proving pipeline to keep its uncovered tail at most $n$ blocks
forever. Lean proves a threshold that is sufficient, starting from a
proving backlog of at most $n/2$ blocks, and necessary over the
pipeline's steady states when proving one block takes less than a slot (\code{slot\_time\_sufficient},
\code{slot\_time\_necessary}). Section~\ref{sec:impl} evaluates it at the
measured proving costs.

\section{Implementation and measurements}
\label{sec:impl}

\paragraph{One source, three uses.} The reference implementation is one
Rust file, \code{rust/src/lib.rs}. It is written in the subset of Rust
that the Charon + Aeneas toolchain translates to Lean~4. The same file
gives three things.

\emph{The native validator.} Its Lean translation is proved sound against
the model: if the code accepts a chain, the chain is valid in the model
(\code{rust\_valid\_chain\_sound} and companions). Safety needs only this
direction; the other direction matters only for liveness. Soundness is
what carries Theorem~\ref{thm:lc} to the shipped code
(\code{rust\_timed\_certified\_agreement}).
\begin{itemize}
\item Id formation is checked by the hashing layer, not by the validator.
  So this theorem, and its TypeScript twin, take it as an assumption on
  the blocks shown (\code{hFormedS}) and at each certificate step.
\item The Rust theorem lets the two chains be checked under two crypto
  contexts, provided every signature the second accepts, the first
  accepts too (\code{hCryptoSig}). With a single context, as in a
  deployment, this holds trivially.
\item The bridges cover the validator's core rules and its key-version
  checks (\code{rust\_valid\_chain\_sound},
  \code{rust\_valid\_chain\_k\_sound}). The three rotation pins of
  Section~\ref{sec:rotation} are, today, checked in the model only.
\end{itemize}

\emph{The circuit.} The same source has a validator that is generic over
its backend (\code{valid\_chain\_be}). Run over plonky2, it is the
certificate's circuit, so the certificate proves exactly the rule that
was verified, for every $n < 2^{63} - 1$
(\code{valid\_chain\_be\_validChain}). That each circuit
gadget is faithful is the one remaining trust assumption; it is stated,
not proved.

\emph{A TypeScript twin.} \code{moltPetit.ts} reaches Lean through an
independent compiler, Thales, with its own soundness bridge carrying
Theorem~\ref{thm:lc} to it (\code{ts\_timed\_certified\_agreement}). The
vendored output corrects three recorded compiler bugs by hand
(\code{tools/thales-reemission/}); those corrections are hand-audited and
part of the trusted base. The twin shows the method is not tied to one
language. Keeping two implementations honest against one model is also
what kept the model abstract.

\paragraph{What is trusted.}
\begin{itemize}
\item the Lean kernel;
\item the pinned translators: Charon + Aeneas, Thales with its recorded
  hand corrections, and the circuit gadgets;
\item that the named assumptions match the deployed primitives.
\end{itemize}
Cryptography enters only as theorem assumptions. Keys, signatures,
certificates and payload commitments are opaque to the protocol, which is
also why no assumption about either language's number model reaches any
theorem.

\paragraph{Measurements.} The prototype pairs the consensus rule with a
minimal application: a committed key set that changes by signed
rotations.
\begin{itemize}
\item Proof system: plonky2~\cite{plonky2} over its native 64-bit field
  (Goldilocks), with Poseidon hashing~\cite{poseidon}.
\item Signatures: SPHINCS+~\cite{sphincsplus,fips205} over Poseidon
  (parameter set \code{128s}).
\item Hardware: one Intel i5-13500 (14 cores, 20 threads), wall-clock
  times.
\end{itemize}
``Circuit rows'' measures the size of what the prover proves; proving
cost grows with it. The \emph{recursion floor} is the fixed minimum cost
of checking one proof inside another.

Two points matter for deployment.
\begin{itemize}
\item \emph{Consensus is nearly free.} The verified validator adds almost
  nothing to what the application already pays for signatures.
\item \emph{The slot time follows.} The measured costs feed the slot-time
  rule of Section~\ref{sec:liveness}. On this hardware, with $n = 7$, it
  gives $\tau \approx 4$\,s, the figure used throughout the paper.
\end{itemize}
Where stateful signatures are acceptable, XMSS~\cite{xmssrfc} over the
same Poseidon gadgets shrinks the in-circuit verifier from $2^{13}$ to
$2^{10}$ rows and makes full certificates about $10\times$ faster. The
price is one-time keys, whose bookkeeping the consensus layer already
does.

\section{Related work}
\label{sec:related}

\paragraph{Density in proof-of-stake.} The closest relatives of the
density rule are in the Ouroboros family, where density is central.
Genesis~\cite{genesis} resolves deep forks by comparing how fast each
grew just after their last common block, which means replaying history.
Samasika~\cite{samasika}, Mina's consensus, carries a constant-size
summary of the minimum window density. It is the closest earlier pairing
of density with succinct proofs.

The key difference: in every Ouroboros variant, density decides
\emph{fork choice}, so finality is probabilistic and grows with depth. In
Molt Petit, density is a hard \emph{validity rule}, so finality is
certain at a fixed depth of $n$ blocks. Molt Petit also uses an equally
weighted roster with a public round-robin leader, $s \bmod n$. The
Ouroboros line is stake-weighted, with private, VRF-based leader election
from Praos~\cite{praos,ouroboros} on. And Molt Petit's security argument
is machine-checked, not written by hand.

\paragraph{Succinct certificates and light clients.} Mina~\cite{mina}
came first with a constant-size recursive certificate; its SNARK attests
the \emph{whole} history. Molt Petit's certificate is useful only
together with the recency check: it gives agreement on recent chains, not
on all of history. Plumo~\cite{plumo} syncs ultralight clients with
SNARK-proved committee hand-offs, argued on paper over a weighted
committee.

The proof-of-work approaches are probabilistic by nature:
NiPoPoWs~\cite{nipopow} use rare superblocks and FlyClient~\cite{flyclient}
uses random sampling. Both certify accumulated \emph{weight}. Molt Petit's
certificate is one recursive proof of a deterministic validity rule:
constant size, with no sampling.

\paragraph{BFT with certain finality.} Like Tendermint~\cite{tendermint}
and HotStuff~\cite{hotstuff}, Molt Petit has a fixed set of participants,
rotating leaders and certain finality, but it gets there the opposite
way. They finalize by \emph{voting}, with quorum certificates. Molt Petit
exchanges no votes at all. The same $2n/3$ threshold is enforced by
counting blocks in a window, and the light client's constant-size object
is a proof of that counting rule, not a bundle of votes.

\paragraph{Long-range attacks, key evolution, weak subjectivity.} Keys
that leak after the fact are the classic long-range threat, for
proof-of-stake and permissioned chains alike~\cite{stakebleeding}. Two
remedies dominate.
\begin{itemize}
\item \emph{Key-evolving (forward-secure) signatures}~\cite{forwardsec},
  as in Ouroboros Praos~\cite{praos}, make an old key useless once its
  holder erases it.
\item \emph{Weak subjectivity}~\cite{weaksubj} has a client that was
  offline too long fetch a recent checkpoint from a trusted source.
\end{itemize}
Molt Petit's recency check is the weak-subjectivity condition turned into
a theorem assumption. But it checks the tip's age against the client's
own clock, not against a trusted checkpoint. A client may sleep for any
length of time and needs no trusted party on waking. The windowed budget
says exactly which leaks a fork can still use: only those that recency
rejects (Theorems~\ref{thm:lc} and~\ref{thm:forge}).

Against theft, mode 2's public schedule does the job of key evolution
without erasure: a retired key is dead by the validator's rule, not by
being destroyed. Mode 3 is the variant that relies on erasure, with free
timing. Key-insulated signatures~\cite{keyinsulated,keyinsulatedsig}
provide the version independence both modes need.

\paragraph{Machine-checked consensus.} Velisarios~\cite{velisarios} (BFT
in Coq), Verdi~\cite{verdi} (Raft, extracted to OCaml) and
IronFleet~\cite{ironfleet} (Paxos-based replication in Dafny) all prove
running consensus code correct. Molt Petit differs in two ways.
\begin{itemize}
\item \emph{What is proved:} a vote-free density consensus, with a
  recursive light-client certificate.
\item \emph{Which way the code flows.} Those systems extract code from a
  model inside the prover. Molt Petit \emph{imports} the deployed sources
  into Lean~\cite{lean,mathlib}, with Charon + Aeneas~\cite{aeneas} and
  Thales~\cite{thales}, so the theorems are about code that already runs.
\end{itemize}
A trusted translation step remains, in the same place extraction sits in
those systems. It just points from the shipped code into the prover, not
out of it.

\section{Limitations and future work}
\label{sec:limitations}

\paragraph{What the design gives up.} Four properties of the systems
above are traded away on purpose. A deployment should know it is doing
without them.
\begin{itemize}
\item \emph{Changing membership.} The roster is fixed and closed. Signing
  keys rotate (Section~\ref{sec:rotation}); validators do not change.
\item \emph{Stake.} Validators have equal weight, and the leader schedule
  is public. A predictable next leader is easier to censor; in return, no
  randomness beacon is needed.
\item \emph{Recovery from halts.} There is no view change and no
  fork-choice repair. If a complete window ever has fewer than $\quorum$
  blocks, the gap can never be filled, and the chain halts for good. This
  is by design. The liveness theorems assume the budget that has then
  failed; safety is unaffected. Concretely: at $n = 7$ and
  $\tau \approx 4$\,s, three validators missing their slots within one
  window of about $28$\,s halts the deployment forever.
\item \emph{Safety without clocks.} The recency check reads a clock, so
  Assumption~\ref{ass:clock} matters for safety, not only for liveness.
  What is never assumed is a synchronous network: in every safety
  theorem, the attacker controls delivery completely.
\end{itemize}
The trade is plain. A closed, equally weighted roster with no recovery is
what lets finality be a validity rule, decided at depth $n$, instead of a
fork-choice score that settles slowly and only with high probability.

\paragraph{What is not machine-checked.} Beyond the trusted base of
Section~\ref{sec:impl}, everything not checked by machine is a named
assumption of the theorem that uses it:
\begin{itemize}
\item the deployment assumptions of Section~\ref{sec:assumptions};
\item id formation, checked by the hashing layer outside the validator
  (\code{hFormedS} in the implementation bridges);
\item for mode 3 and the untimed form of mode 2, honest custody per key
  (Assumption~\ref{ass:rotation-honest}), assumed rather than derived;
\item version independence of keys under theft (provided by
  key-insulated signatures~\cite{keyinsulatedsig});
\item the circuit's trust anchor outside the circuit: the roster's
  commitment to the cold roots;
\item the recency check itself, which runs in the unverified node loop
  because the pure validators carry no clock (passing $\mathit{now}$
  through them is routine future work);
\item the operational duties of Section~\ref{sec:rotation}: moving
  together and erasure in mode 3. In mode 2, key provisioning is charged
  to the budget, not assumed.
\end{itemize}
That the circuit gadgets are faithful is stated, not proved. The
equivalence lemma, \code{valid\_chain\_be\_validChain}, is proved for
the native 64-bit instantiation, for every $n < 2^{63} - 1$, where its
quorum arithmetic cannot overflow.

\paragraph{The long-range residual.} Exposure after a window's stretch of
time does not count against it. So a patient attacker can collect
signatures from keys exposed late, stolen or reached through a signer it
controls for a while, into an arbitrarily long fork on old slots. Such a
fork is stale forever, and harmless to any client that applies the
recency check of Theorem~\ref{thm:lc}. Theorem~\ref{thm:forge} forbids
preparing one in advance. But it is never impossible.

Two options would remove it, each at a price:
\begin{itemize}
\item forward-secure signatures~\cite{forwardsec} with erasure, which
  need a stateful signer;
\item counting every exposure forever
  (\code{exposure\_agreement\_ever\_on} covers this budget, for full
  chains), which charges a cleaned-up signer to the budget for good.
\end{itemize}
Key rotation does not remove it. In mode 2, a stolen current key passes
the pin for every older slot. In mode 3, a fork may switch to the current
generation where it branches. In both, a late theft can still sign old
slots, into a fork that recency rejects. Consensus-managed one-time keys
(the XMSS variant of Section~\ref{sec:impl}) move key state into the
chain and complement this. We keep the windowed budget, the weakest of
these assumptions, and accept the contained residual.

\paragraph{Artifact.} The repository builds with one command,
\code{lake build}. That covers the model and its results, both
implementation bridges, the \code{Molt} library with its axiom guards, and
\code{Spec/} with the cited results (\code{Paper/Proofs.lean}). A fresh
checkout re-checks every theorem cited in this paper that way.

Separately, the repository's \code{nix flake check} re-checks that the
vendored translations are exactly what the pinned translators (Charon +
Aeneas; Thales) produce from \code{rust/src/lib.rs} and
\code{moltPetit.ts}. It checks faithfulness only, not the proofs. What no
machine re-checks is the trusted base above: the translators and circuit
gadgets themselves, and the hand-audited corrections.
