The vacuity defect, in full

This is the one finding that would have been embarrassing in review, so it is worth stating completely. W3b originally shipped a theorem intended to be the headline separation: 

-- ORIGINAL, DEFECTIVE
theorem pacedStolenAt_safe_under_tight_unsafe_under_untimed
    {n Δconf P d : Nat} (hn : 1 ≤ n) (hP : n + d ≤ P)
    {c₀ : Chain} {ι : Nat → Nat} (hInj : Function.Injective ι)
    (hRange  : ∀ k, k < n → ι k < n)
    (hFloor0 : ∀ k, k < n → ∀ s, s < n → inForce n Δconf c₀ (ι k) s = 0)
    (hReacts : Reacts n Δconf d c₀ (pacedStolenAt ι P))            -- ← the problem
    (hNoBack : NoTheftBackdating n Δconf c₀ (pacedStolenAt ι P))   -- ← the problem
    {rented : ByzantineSlots} {m : Nat} (hm : faultBudget n < m) (hmn : m ≤ n) :
    (∀ u, (recentTheftProducersTight n d (pacedStolenAt ι P) u).card ≤ 1) ∧
      ¬ (badSlotsIn (badKeyrot n Δconf rented … c₀) 0 n).card ≤ faultBudget n

hFloor0 and hReacts are contradictory whenever d < n. The paced schedule's first theft is at real slot 0 · P = 0, so Reacts forces the victim's floor strictly above 0 at every slot from d onward, while hFloor0 pins that same floor to 0 across all of [0, n). Any slot in [d, n) witnesses the contradiction. This was not reasoned about on paper — it was proved in Lean before anything was changed: 

theorem w3b_combined_vacuous_when_d_lt_n
    {n Δconf P d : Nat} (hn : 1 ≤ n) (hdn : d < n) … :
    False := by
  have htheft : pacedStolenAt ι P (ι 0) 0 0 := ⟨rfl, by simp⟩
  have hpos : 0 < inForce n Δconf c₀ (ι 0) d := hReacts (ι 0) 0 0 htheft d (by omega)
  have hzero : inForce n Δconf c₀ (ι 0) d = 0 := hFloor0 0 hn d hdn
  omega
Provenance of that snippet — it is not a repository artifact

w3b_combined_vacuous_when_d_lt_n was a throwaway scratch file, compiled once against the live toolchain to settle the question and then deleted. It is not committed and grep will not find it in the repo. It is reproduced here because it is the evidence for the claim, but a reviewer should treat it as the transcript of a check that was run, not as a checked-in theorem. The consequences of that check — the dropped hypotheses, paced_separation_witnessed, and paced_budget_holds_under_timing — are all committed and axiom-guarded.

Why it mattered

d is the reaction delay. d < n — reacting inside one window — is precisely the attractive deployment regime. So the theorem said nothing exactly where a reader would most want it to speak, while its name and docstring advertised a headline separation.

The fix. Neither conjunct ever used the two timing hypotheses, so they were dropped. The theorem is now non-vacuous, and a second theorem discharges every remaining hypothesis at concrete parameters — a separation with no hypotheses at all: 

theorem paced_separation_witnessed :
    (∀ u, (recentTheftProducersTight 4 1 (pacedStolenAt id 5) u).card ≤ 1) ∧
      ¬ ((badSlotsIn (badKeyrot 4 0 (fun _ => False)
            (MoltPetit.Model.stolenOf (pacedStolenAt id 5)) []) 0 4).card ≤ faultBudget 4) := by
  refine ⟨fun u => recentTheftProducersTight_card_le_one_of_paced (by omega) u, ?_⟩
  exact pacedStolenAt_exceeds_untimed_budget (n := 4) (Δconf := 0) (P := 5)
    (by omega) Function.injective_id (fun k hk => hk)
    (fun _ _ _ _ => rfl) (m := 2) (by decide) (by omega)

At n = 4, d = 1, P = 5, victims ι = id, empty witness chain: the tight census is 1 at every window while the untimed bad-slot count at window 0 already exceeds faultBudget 4 = 1. This also closes a gap the original design had knowingly left open — it had recorded the hypotheses as "never shown jointly satisfiable", which understated the problem.

The impossibility result — and what the paper may therefore claim

Removing the hypotheses raised the obvious question: could the intended separation be recovered with a better witness? The answer is no, and this is now a theorem rather than a caveat: 

theorem paced_budget_holds_under_timing
    {n Δconf d P : Nat} (hn : 0 < n) (hP : n + d ≤ P) {ι : Nat → Nat} {c₀ : Chain}
    {rented : ByzantineSlots} {Rrent : Nat}
    (hReacts : Reacts n Δconf d c₀ (pacedStolenAt ι P))
    (hNoBack : NoTheftBackdating n Δconf c₀ (pacedStolenAt ι P))
    (hRent : ∀ u, (badSlotsIn rented u n).card ≤ Rrent)
    (hRT : Rrent + 1 ≤ faultBudget n) :
    ∀ u, (badSlotsIn (badKeyrot n Δconf rented
        (MoltPetit.Model.stolenOf (pacedStolenAt ι P)) c₀) u n).card ≤ faultBudget n

Under the two timing hypotheses the paced adversary satisfies the old, untimed budget. The mechanism is theft_exposure_window: the hypotheses confine each theft's exposure to an interval of fixed width d, and pacing n + d ≤ P puts at most one such interval in any window — so even the cumulative census is bounded by 1 everywhere (exposedProducers_card_le_one_of_paced).

The consequence for the paper

There is no execution in which the timed hypotheses hold and the untimed budget fails. The gain from theft times is therefore not that safety changes; it is that a deployment is asked to attest something different and defensible — a fixed per-window concurrency bound instead of a per-stretch total that grows with the stretch. The AN/29 answer as originally given ("a theft charges only windows at or after it … and F_max rises") is accurate; what needed sharpening is the reason, and any sentence implying an execution-level separation must be avoided.
